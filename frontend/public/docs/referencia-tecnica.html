Guía para incorporarse al proyecto

Dónde nace, viaja y se guarda cada dato

HCOP JP es un monolito modular Java 21. La vista web conserva la experiencia clínica; Spring MVC expone el contrato; los servicios ejecutan reglas y transacciones; los repositorios acceden a PostgreSQL.

Spring BootSpring MVCJDBCFlywayPostgreSQLOpenAPI

Arquitectura MVC

Viewsrc/main/resources/static
ControllerRutas, entrada, sesión, permisos
ServiceReglas, idempotencia, transacción
RepositorySQL parametrizado y mapeo
PostgreSQLDatos, restricciones y auditoría
  • Un controlador no contiene SQL ni reconstruye reglas clínicas.
  • Un servicio coordina escrituras relacionadas bajo @Transactional.
  • Un repositorio no conoce HTTP, cookies ni elementos visuales.
  • La vista usa las rutas compatibles bajo /api/**.
  • Flyway es el único mecanismo permitido para cambiar el esquema.

Sesión, roles y permisos

POST /api/auth/login crea una cookie HCOP_SESSION HttpOnly y SameSite Strict. Cada ruta protegida resuelve la sesión, comprueba estado del usuario y exige el permiso específico antes de entrar a la regla clínica.

Los identificadores de paciente son locales. Los diagnósticos se acumulan; no se sobrescribe un cáncer anterior. Un tratamiento referencia al paciente y, cuando corresponde, al diagnóstico seleccionado.

JSONB con criterio: se usa para la hoja flexible y snapshots clínicos. Identidad, relaciones, fechas, estados, revisiones y restricciones operativas permanecen en columnas tipadas.

Tratamiento, ciclos y Hospital de Día

  1. La prescripción exige un diagnóstico perteneciente al paciente.
  2. El protocolo aporta drogas, requisitos, intervalo, duración estimada y grupo clínico. Si este último contradice un diagnóstico reconocible, se exige una confirmación explícita y su justificación.
  3. Al guardar se crean tratamiento, snapshot, ciclos logísticos y evolución en una transacción.
  4. Cada ciclo pendiente reaparece según la fecha calculada hasta ser turnado, suspendido o completado.
  5. Farmacia marca medicación recibida o en poder del paciente y puede imprimir el QR.
  6. El turnero reserva tantos intervalos como exige la duración y PostgreSQL impide superposiciones.
  7. El escaneo verifica firma, documenta el acto, abre la aplicación correcta y permite finalizar.

Archivos clínicos

Los binarios nunca se sirven como estáticos públicos. La API valida tamaño, extensión, tipo declarado y firma binaria; genera un nombre interno; guarda metadatos; y entrega el archivo sólo a una sesión autorizada. La eliminación durante la misma sesión requiere un token temporal específico.

API y Swagger

Springdoc genera OpenAPI 3 en ejecución. La documentación se divide en API completa, clínica y administración/configuración.

  • /swagger-ui.html: interfaz navegable.
  • /docs/api-endpoints.html: catálogo buscable con todos los endpoints y permisos.
  • /v3/api-docs/hcop-jp-completa: contrato completo JSON.
  • /v3/api-docs/clinica: contrato clínico.
  • /v3/api-docs/administracion: administración.
Swagger usa la misma cookie de sesión del navegador. “Try it out” no evita roles, permisos, control de revisión ni validaciones clínicas.

Concurrencia e integridad

  • Documentos, configuración, turnos y estados usan revisión optimista.
  • La exclusión de intervalos en PostgreSQL evita turnos superpuestos incluso con dos usuarios a la vez.
  • Las claves foráneas impiden tratamientos o archivos huérfanos.
  • Las evoluciones generadas por flujos clínicos son inmutables e idempotentes.
  • Flyway valida migraciones aplicadas y tiene limpieza destructiva deshabilitada.

Cómo extender sin romper contratos

  1. Describir el caso clínico, permiso y regla de auditoría.
  2. Crear una migración Flyway aditiva si cambia persistencia.
  3. Implementar Repository, Service y Controller en ese orden conceptual.
  4. Mantener la ruta compatible que consume la vista o versionarla explícitamente.
  5. Documentar la operación en OpenApiConfiguration.
  6. Agregar una comprobación al script integral y verificar Docker.
